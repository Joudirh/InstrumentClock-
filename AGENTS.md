# AGENTS.md

Static front-end (Vite, vanilla ES6 modules, plain CSS) plus a small TypeScript backend: Prisma 7 -> Neon Postgres and Neon Object Storage (S3-compatible) used by Vercel serverless functions in `api/`.

## Commands
- Setup: `npm install` (postinstall generates the Prisma client) then `cp .env.example .env` and fill `DATABASE_URL`, `DIRECT_URL`, `AWS_*` — `lib/prisma.ts` throws at import time if `DATABASE_URL` is missing, so dev/migrate/seed all fail without `.env`.
- `npm run dev` — Vite dev server (run from repo root)
- `npm run build` — `vite build` output to `dist/` (front-end only; API is built by Vercel)
- `npm run preview` — serve the build
- `npm run db:push` / `npm run db:migrate` — sync schema to Neon (`prisma migrate dev` creates `prisma/migrations`)
- `npm run db:deploy` — apply committed migrations (used on Vercel)
- `npm run db:seed` — `tsx prisma/seed.ts`; idempotent upserts from `prisma/seed-data.ts` (sessions/categories/instruments 72–150 + `instrument_windows`). Never wipes. `js/data.js` is only the front-end static fallback now.
- `npm run db:studio` — Prisma Studio (very slow to boot here; expect minutes)
- `npm run assets:upload` — upload `public/assets/*` to the S3 bucket and upsert `Asset` rows
- Admin pages: `/admin` (login) and `/dashboard` (sidebar) are extra Vite entry points (`admin.html`/`dashboard.html`, configured in `vite.config.js`; `cleanUrls` in `vercel.json` + a dev rewrite give `/admin` and `/dashboard`). Admin user is seeded by `npm run db:seed` (`admin@instrumentclock.com` / `admin123@`, `users` upsert in `prisma/seed.ts`).
- Admin APIs: `/api/auth/login|logout|session` (HttpOnly cookie `ic_session`, DB tokens in `user_auth_tokens`, helpers in `lib/session.ts`, scrypt hashes in `lib/password.ts`) and `/api/admin/*` (`overview`, `instruments` full CRUD, `users`, `categories`, `sessions`) — all guarded by `requireAuth`. On instrument create/update the legacy `openHour/openDay/...` columns are re-derived from `instrument_windows` (`deriveLegacyColumns` in `lib/admin-data.ts`).
- Market-hours helpers: `lib/market-hours.ts` (Intl-based, DST + midnight-crossing aware); ad-hoc checks: `npx tsx scripts/market-hours-check.ts`.
- No tests, linter, or typecheck script exist; Vite/Vercel/tsx transpile without type-checking. `npx tsc --noEmit` covers `api/ lib/ prisma/ scripts/` + `prisma.config.ts` but is wired to nothing (tsconfig excludes only `node_modules`/`dist`, so expect errors from `lib/generated/` — ignore those). Run it manually as the only typecheck.

## Constraints / gotchas
- **Prisma 7 requires a driver adapter.** `lib/prisma.ts` uses `@prisma/adapter-neon`; `new PrismaClient()` without an adapter throws. Keep `prisma`, `@prisma/client`, `@prisma/adapter-neon` on the same version (pinned `7.10.0`).
- **Connection URLs are configured in `prisma.config.ts`, not `schema.prisma`** (the `datasource` block has no `url`). CLI commands use `DIRECT_URL` (unpooled, host without `-pooler`); the app uses the pooled `DATABASE_URL`.
- **The Prisma client is generated to `lib/generated/prisma` and is gitignored.** It must be regenerated on every fresh install/clone (`postinstall` runs `prisma generate`). Never edit generated files.
- **Editing `schema.prisma` requires regenerating the client AND restarting `npm run dev`.** `prisma generate` alone is not enough: `vite.config.js`'s `ssrLoadModule` caches `lib/prisma.ts` (and its generated client) for the dev server's lifetime, so the API keeps serving the old shape until you restart. Symptom of forgetting: the API returns old field names.
- **The Neon DB can drift from `schema.prisma`.** Seen before: the `20261014191817_init` migration was marked applied while the live `instruments` table had *old* columns (`schedule_days`, `schedule_tz`, `optimal`); fixed by rewriting the init migration and re-basing Neon. If symptoms suggest drift, verify actual columns with `SELECT column_name FROM information_schema.columns WHERE table_name='instruments'`. Fix a drifted dev DB with `npx prisma db push --force-reset` then `npm run db:seed` (destructive: recreates tables; the CLI may require `--accept-data-loss`/consent, see below).
- **`js/api.js` swallows API failures and silently falls back to static `js/data.js` (`source: 'static'`).** So "the front loads but shows no DB data / wrong hours" is almost always the API 500-ing (drift or stale client), not a front-end bug. Check `/api/instruments` directly first.
- The API→front mapping in `js/api.js` (`mapInstrument`/`mapSession`) is a contract with `prisma/schema.prisma` — renaming a column means editing both.
- **Prisma blocks destructive commands run by an agent.** `prisma db push --force-reset` (and `--accept-data-loss` with existing rows) is refused with an "invoked by OpenCode" error unless you set `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` to the user's verbatim consent, and you must get explicit confirmation first.
- `package.json` is `"type": "module"` because the Prisma 7 client is ESM-first. The browser files in `js/` are loaded via `<script type="module">` and are unaffected.
- `js/*.js` import Luxon from a CDN ESM URL (not an npm dep); dev/build need network access. Changing the Luxon version means editing every import.
- Flag images are referenced with absolute `/assets/<file>.png` paths (in `js/timeline.js`) and live in `public/assets/`. Serve from the repo root; opening `index.html` directly breaks modules and these paths.
- **Seed source of truth is `prisma/seed-data.ts` (TypeScript), not `js/data.js`.** Editing instruments/sessions means editing it and re-running `npm run db:seed`. Instruments are declared as compact `Row` entries: `sessionSlug`, `t:` (trading) / `o:` (optimal) windows as `"HH:MM-HH:MM"` spans (timezone defaults to the session's), and a one-line `description` in the `DESCRIPTIONS` map keyed by instrument id. `js/data.js` is only the front-end static fallback; don't try to keep both in sync.
- Seed validation is strict: every instrument must have at least one TRADING **and** one OPTIMAL window (abort with no writes otherwise); windows use minutes-of-day, `endMinute` may exceed 1440 (up to 2880) for midnight-crossing; days are `1..7`. Schema note: legacy `openDay/closeDay/openHour/...` columns are derived only on instrument **create** (updates never touch them); the front reads the normalized `instrument_windows` instead.
- `DOCUMENTATION.md` is partly stale (says to open `index.html` directly, references `assets/*`); trust the code. `README.md` is also partly stale (says `db:seed` fills the DB from `js/data.js` — no longer true).
- **The dev middleware must mirror Vercel's request contract.** Vercel gives handlers `req.body` (parsed JSON), `req.query`, `req.cookies`; `vite.config.js`'s `apiDevMiddleware` shims all three before calling the handler. If a new handler uses another Vercel-only convenience (e.g. `res` redirect helpers), shim it there too.
- Window times are minutes-of-day; `endMinute` can go up to 2880 (cross-midnight) and the admin UI displays it as "HH:MM" with hours > 24 (e.g. 25:30 = 01:30 next day). Don't switch the editor to `<input type="time">` — it cannot represent cross-midnight ends.

## Architecture
- Front-end: `index.html` entry; `js/main.js` wires state, events, render calls. `js/data.js` (data), `js/timezone.js` (Luxon conversions, DST via `seasons`), `js/timeline.js` (Forex timeline), `js/ui.js` (lists/filters/clocks), `js/bell.js` (open-markets bell in the filters bar: green/red badge count + dropdown grouped by session; refreshes every clock tick, DOM writes only when the count changes). Theme via `data-theme` on `<html>`, persisted in `localStorage`.
- Backend: `lib/prisma.ts` (client singleton), `lib/s3-client.ts` (S3 client + `uploadFile`/`ensureBucket`/`getSignedAssetUrl`), `scripts/upload-assets.ts`, `prisma/seed.ts`, `prisma/schema.prisma`.
- API (Vercel, default export `(req, res)`): `api/instruments.ts`, `api/sessions.ts`, `api/health.ts`. The front-end loads data via `js/api.js` (`fetchAppData` → `/api/instruments` + `/api/sessions`), mapping DB rows to the front shape, and **falls back to static `js/data.js`** if the API is unreachable.
- `vite.config.js`: a dev-only middleware (`apiDevMiddleware`, `apply: 'serve'`) runs `api/*.ts` through `ssrLoadModule` during `vite dev`, so `npm run dev` reflects the Neon DB locally (Vite doesn't serve serverless functions otherwise). Admin front-end modules live in `js/admin/` (`app.js` hash router + auth guard, `common.js`/`modal.js`, `sections/*.js`); menus mirror the DB tables (users, instruments, categories, sessions).
- Deploy: `vercel.json` runs `prisma generate && prisma migrate deploy && vite build`. Set `DATABASE_URL`, `DIRECT_URL`, and the `AWS_*` vars in the Vercel project (they live in `.env`, which is gitignored). Bucket creation is handled by `ensureBucket` / `npm run assets:upload`.
  - These vars must be **available at build time** (set for the right environment, not sensitive-only); otherwise `migrate deploy` fails with "Connection url is empty" while `generate` still passes. `prisma.config.ts` now throws a clearer error for that case.
